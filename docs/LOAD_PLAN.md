# План первинного навантаження

Цільовий стенд: sandbox API + справжній PostgreSQL 16, один Uvicorn worker.
Locust запускається на Windows-хості, сервери — у Docker Desktop. Не запускати проти production.

| Профіль | VUsers | Spawn rate | Ramp-Up | Тривалість | Місткість |
|---|---:|---:|---:|---:|---:|
| normal | 10 | 2/с | 5 с | 60 с разом із розгоном | 10 |
| spike | 50 | 10/с | 5 с | 60 с разом із розгоном | 10 |

Перед відліком скрипт створює окремих користувачів та новий курс через HTTP API.
Реєстрація не входить у виміряні 60 секунд. Вхід кожного VUser входить у вимірювання.
Normal: GET /courses (вага 3), GET /enrollments/me (1), одноразовий POST enroll (1),
після нього GET /users/me. Пауза між задачами 0.3–0.8 с.
Spike: кожний VUser входить, чекає спільного моменту t=15 с і один раз надсилає enroll;
після цього читає каталог і свої записи з паузою 0.2–0.4 с.
Це кероване моделювання відкриття запису «опівночі», а не очікування реальної півночі.
Якщо логін VUser завершився пізніше 15 с, він приєднається пізніше — це видно в журналі.

## Виходи

`python scripts/run_load.py normal`, потім `python scripts/run_load.py spike`.
Вводяться ім'я й пароль адміністратора sandbox. У results/local/ створюються окремі каталоги:
load_stats.csv, load_stats_history.csv, load_failures.csv, load_exceptions.csv,
locust.html, locust.log, outcomes.json, resources.csv, metadata.json, summary.json,
SUMMARY.md та latency_rps.png (коли є непорожня історія).
Після запуску одноразовий файл паролів VUsers видаляється. Тестові акаунти в sandbox залишаються.
Розподілений Locust не підтримується: черга акаунтів розрахована на один процес.

## Метрики та трактування

RPS — фактичні запити за секунду, не кількість людей. Latency — клієнтський час відповіді,
включно з мережею та очікуванням. p95 Locust — наближений перцентиль гістограми.
На графіку p95 — ковзне значення; в summary — за весь запуск, тому вони можуть відрізнятися.
HTTP 409 Course is full/Already enrolled очікувані та позначаються success у Locust;
їх кількість і причини окремо у outcomes.json. Error Rate — частка неочікуваних збоїв,
а не частка всіх HTTP 4xx. Для spike очікується 10 успішних записів та 40 відмов
через відсутність місць, якщо всі 50 користувачів дійшли до спроби без збоїв.
Ці числа — критерій перевірки, не вже отримані результати.

CPU/RAM: docker stats для api і db; CPU 100% приблизно відповідає одному ядру,
RAM — показник Docker, а не вся пам'ять VM Docker Desktop. Збір приблизно кожні кілька
секунд: два docker stats виконуються послідовно, тому timestamps не є суворо рівномірними.
Для native API можна передати --pid та --db-pid; тоді вимірюється process CPU і сумарний RSS
процесів, виявлених на початку, зі можливим подвійним обліком shared pages.
Locust і сервер на одному ПК конкурують за CPU, тому це навчальний baseline, не production benchmark.

## Аналіз після запуску

1. Перевірити metadata.locust_exit_code, capacity_invariant_ok та помилки збору ресурсів.
2. Зіставити spike t=15 с зі зміною p95, RPS, CPU і кількістю 409.
3. Розглядати per-endpoint рядки CSV: загальний mean може приховати повільний enroll.
4. Повторити щонайменше 3 рази на нових курсах і порівняти розкид.
5. Для пошуку межі збільшувати користувачів і тривалість окремим експериментом.

Можливі обмеження: серіалізація запису на одному course row, Argon2 під час масового входу,
пул SQLAlchemy (10 + 10 з'єднань), thread pool, CPU/RAM хоста. Це гіпотези, а не виміряні вузькі місця.
У Work цільовий тест не проводився: PostgreSQL/Docker недоступні для виконання.
Числові результати та графіки фактичного навантаження потрібно сформувати наведеними командами.
