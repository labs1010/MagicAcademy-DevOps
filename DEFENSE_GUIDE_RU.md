# Защита Magic Academy за два часа

Цель подготовки — уметь показать работающий сценарий и объяснить каждую его часть.
Не заучивай весь Python. Сначала пройди START_GUIDE и выполни PostgreSQL/Docker-проверки
на своём компьютере: в Work они не запускались. Без собственного запуска нельзя честно
утверждать, что ты измерил производительность или проверил сохранность Docker-данных.

## 1. Короткий рассказ о проекте

«Я сделал платформу записи в Магическую Академию. Пользователь регистрируется, входит,
смотрит курсы и записывается, если есть место. Администратор создаёт курсы. В основе
FastAPI и PostgreSQL. Я тестирую всплеск записи на популярный курс и запускаю приложение
вместе с базой через Docker Compose».

ЛР1 заложила структуру, архитектуру, Git, Ruff и pre-commit. ЛР2 добавила пользователей,
роли, запись и тесты. ЛР3 отделила конфигурации sandbox/production и настроила CI.
ЛР4 добавила Locust и сбор результатов. ЛР5 упаковала то же приложение в контейнеры.
Это один развиваемый проект, не пять независимых программ.

## 2. Путь HTTP-запроса

Клиент отправляет, например, `POST /courses/1/enroll` и заголовок `Authorization: Bearer ...`.
Uvicorn принимает HTTP-соединение и передаёт запрос ASGI-приложению FastAPI. FastAPI
выбирает обработчик по методу и пути, преобразует course_id в целое число и выполняет
зависимости. `current_user` проверяет подпись JWT и срок действия, получает пользователя из БД.
Функция enroll проверяет бизнес-правила и возвращает объект Enrollment. Pydantic
превращает его в JSON по EnrollmentOut, FastAPI возвращает 201.

Если токен отсутствует или недействителен — 401. Если пользователь известен, но прав нет — 403.
Неправильные входные данные — 422, отсутствующий курс — 404, занятое место или дубль — 409.
Неожиданная ошибка сервера — 500 с общей фразой; traceback остаётся в серверном журнале.

Синхронная функция `def` не делает всю систему последовательной: FastAPI запускает её
в пуле потоков. Поэтому несколько запросов действительно могут одновременно дойти до БД.
`async def` сам по себе не ускоряет блокирующие SQL-запросы; здесь сознательно выбран sync ORM.

## 3. Python и PostgreSQL

SQLAlchemy Engine управляет пулом соединений, psycopg передаёт SQL по протоколу PostgreSQL.
Session — объект одной операции/запроса: через него читаются строки, добавляются объекты,
вызывается commit. Отдельные HTTP-запросы не делят одну Session.

Модели описывают три таблицы. Foreign key означает, что Enrollment ссылается на реального
пользователя и курс. Unique запрещает повтор user_id + course_id. Check запрещает capacity ≤ 0.
ORM помогает писать SQL через Python, но не заменяет ограничения базы.

Пример гонки без защиты: осталось одно место, два запроса одновременно видят count=0,
оба добавляют запись — мест стало на одно больше. В проекте первый запрос берёт
`SELECT ... FOR UPDATE` на строке курса. Второй ждёт. Первый проверяет count, делает INSERT
и commit. Второй получает блокировку, повторно считает уже обновлённые записи и получает 409.
Уникальность предотвращает дубли, но **сама по себе не защищает вместимость**: разные пользователи
не нарушают Unique. Поэтому нужны и транзакционная блокировка, и Unique.

Блокировка PostgreSQL работает между разными процессами API. Обычный Python Lock
работал бы лишь внутри одного процесса. Все пути записи обязаны соблюдать тот же протокол:
прямой SQL INSERT стороннего оператора обходит прикладную проверку вместимости.

## 4. Где входные данные

- HTTP JSON регистрации: username, password. Роль клиент не выбирает.
- HTTP form входа: username, password. Swagger Authorize использует этот endpoint.
- JSON создания курса: title и capacity; доступен только ADMIN.
- course_id и user_id берутся из пути, но идентичность текущего пользователя — из JWT и БД.
- .env/переменные окружения: адрес БД, окружение, ключ подписи, пароли и порт.
- Locust: профиль, число VUsers, spawn rate, длительность, wait_time и момент начала записи.

Пароль хранится как Argon2id-хеш со случайной солью. Восстанавливать пароль из него не нужно:
при входе библиотека проверяет введённый пароль против хеша. JWT подписан, но **не зашифрован**:
содержимое можно прочитать, поэтому паролей там нет. Срок действия — по умолчанию 60 минут.
Роль читается из БД; подмена role в JSON не даёт прав администратора.

IDOR — доступ к чужому объекту через замену его id. Поэтому PATCH профиля сравнивает
user_id из URL с user.id текущего токена, а чтение Enrollment проверяет его владельца.

## 5. Что делает Locust

Один виртуальный пользователь — Python-объект с HTTP-клиентом и собственным токеном.
Он выполняет задачи и делает паузы. 50 VUsers не означает ровно 50 RPS: у одного пользователя
может быть несколько запросов в секунду или один запрос за несколько секунд.

Подготовительный скрипт создаёт новый курс и уникальные аккаунты, затем запускает Locust.
Для normal запускаются 10 пользователей со скоростью 2 новых пользователя/с: разгон 5 с.
Для spike — 50 по 10/с: тоже 5 с. Общая продолжительность каждого опыта 60 с, включая разгон.
В spike пользователи входят заранее и ждут общей отметки 15 с. Затем одновременно пытаются
записаться на курс с 10 местами. Это модель открытия записи, не привязка к настоящей полуночи.

Normal чередует каталог, свои записи и одну попытку записи. Spike после первой попытки
читает данные. Новые курсы на каждом запуске нужны, чтобы второй опыт не начинался на уже
заполненном курсе. Перед тестом регистрацию выполняют отдельно; вход входит в метрики.

## 6. Значение метрик

| Метрика | Что означает | Как читать |
|---|---|---|
| VUsers | Одновременно активные виртуальные пользователи | Модель людей, не соединений БД |
| Ramp-Up | Время набора целевого числа VUsers | users / spawn rate |
| RPS | Запросов в секунду | Выше не всегда лучше: смотреть ошибки и задержки |
| Latency | Время от отправки до ответа | Включает сеть, очередь и работу сервера |
| Mean | Средний latency | Может скрывать редкие очень медленные запросы |
| Min/Max | Самый быстрый/медленный ответ | Max чувствителен к единичному выбросу |
| p95 | Примерно 95% ответов не медленнее этого значения | В Locust оценка по округлённой гистограмме |
| Error Rate | Доля неуспешных запросов по правилам сценария | В этом сценарии ожидаемые 409 вынесены отдельно |
| CPU | Использование процессора | 100% примерно одно ядро, может быть выше 100% |
| RAM | Память процесса/контейнера | Указать способ измерения: RSS или Docker stats |

Пример только для понимания: если 1000 запросов и 20 технических сбоев, Error Rate = 2%.
Это учебный пример, **не результат этого проекта**. 40 ответов 409 при 10 местах и 50 желающих
могут означать правильное ограничение вместимости. Если считать их технической поломкой,
оценка качества будет неверной. Их всё равно надо показывать отдельным счётчиком.

## 7. Как анализировать свой запуск

Открыть SUMMARY.md, исходный load_stats.csv и latency_rps.png. Сначала убедиться, что
запуск завершён, есть запросы и CPU/RAM действительно измерены. Пустые данные — не нули.
Смотреть отдельно enroll и GET: общая средняя величина может спрятать задержку записи.
Сравнить момент всплеска с p95, RPS и ресурсами. Если p95 растёт, а RPS перестаёт расти,
сервер, БД или генератор, вероятно, достигли ограничения; нужно подтвердить причину.

Возможная причина именно здесь — очередь блокировок одного курса. Но без замеров нельзя
сказать «узкое место найдено». Argon2 при массовом логине тоже использует CPU и память.
Пул БД ограничен 20 соединениями (10 обычных + 10 дополнительных), а потоков может быть больше.
Если CPU высокий у Locust, измеряемый предел может принадлежать генератору, а не серверу.

График содержит ковзной p95, итоговая таблица — p95 всего теста. Они не обязаны совпадать.
Один 60-секундный опыт — предварительный baseline. Для вывода о пределе системы нужны более
длинные опыты, несколько повторений и постепенное увеличение нагрузки.

## 8. Docker без магии

Dockerfile — рецепт сборки. Image — полученный неизменяемый набор слоёв с Python,
зависимостями и кодом. Container — запущенный процесс из image с настройками и отдельным
изменяемым слоем. Из одного image можно создать несколько контейнеров.

В builder-стадии создаётся /opt/venv и устанавливаются runtime-зависимости. В runtime
копируется готовое окружение и app; pip-кеш и рабочая папка сборки туда не переносятся.
Базовый Python 3.12-slim одинаковый, поэтому скопированное окружение совместимо.
Компиляторы вообще не устанавливаются: зависимости берутся готовыми wheels.
Multi-stage не означает доказанное уменьшение размера на конкретное число мегабайт:
такое сравнение здесь не измерено.

`WORKDIR /app` задаёт текущую папку. `COPY app ./app` помещает код внутрь образа.
`USER academy` запускает сервер без root. `CMD` запускает Uvicorn на 0.0.0.0:8000
внутри контейнера. Если внутри слушать только 127.0.0.1, опубликованный порт не даст
доступа извне контейнера. EXPOSE — документация порта; публикацию делает ports в Compose.

## 9. Compose, сеть, volume и готовность

Compose читает YAML, создаёт сеть, volume, PostgreSQL и API. Имя сервиса `db`
разрешается внутренним DNS в адрес контейнера БД. `localhost` внутри API означал бы
сам API-контейнер, поэтому для PostgreSQL указан db:5432.

`ports: 127.0.0.1:8000:8000` публикует API только на локальном компьютере. Основная конфигурация
не публикует PostgreSQL наружу. Оба сервиса состоят в отдельной bridge-сети backend.
Это сеть Compose-проекта; флаг `internal: true` здесь не используется. Изоляция БД обеспечена
отсутствием host-порта и подключением только к этой сети, а не абсолютным запретом исходящего трафика.

Named volume pgdata монтируется в /var/lib/postgresql/data. Контейнер можно удалить,
а содержимое volume остаётся. `down` удалит контейнеры и сеть, но сохранит volume;
`down -v` удалит также данные. `stop` только остановит процессы.

`depends_on` задаёт зависимость порядка запуска. Одного порядка недостаточно:
PostgreSQL-процесс может стартовать, но ещё не принимать подключения.
healthcheck запускает pg_isready, а condition: service_healthy задерживает запуск API
до готовности БД. API-healthcheck обращается к /health, который выполняет SELECT 1.
После старта depends_on не гарантирует вечную доступность БД и не делает автоматический failover.
pool_pre_ping помогает обнаружить разорванное соединение при выдаче его из пула.

## 10. Окружения и разработка

`.env` — файл настроек для Compose. Compose подставляет значения в YAML до создания
контейнеров; environment передаёт их процессу Python. Сам файл внутрь образа не копируется.
При native-запуске pydantic-settings читает .env.sandbox/production по APP_ENV.
Production имеет другую БД, ключ, volume и порт, debug=False. Это не означает автоматически
полную готовность к публичному интернету: MVP не настраивает TLS и защиту от перебора паролей.

В dev режиме bind mount связывает локальную папку app с /app/app. Сохранённый файл сразу
виден внутри контейнера, а --reload перезапускает сервер. Bind mount — связь с конкретной
папкой хоста; named volume — хранилище под управлением Docker. Они решают разные задачи.
Под нагрузкой reload выключают, иначе слежение за файлами и перезапуски исказят эксперимент.

## 11. Что сломается при изменениях

| Изменение | Последствие |
|---|---|
| Удалить with_for_update | Возможна переполненная группа при гонке |
| Удалить Unique | Пропадёт дополнительная защита от дублей на уровне БД |
| Удалить проверку владельца | Возникнет IDOR |
| Удалить admin_user dependency | Обычный пользователь сможет создать курс |
| Указать db host localhost в контейнере API | Подключение пойдёт в сам API, БД не найдётся |
| Удалить volume | Данные останутся в слое контейнера и потеряются при его удалении |
| Удалить healthcheck/condition | API может стартовать раньше готовности PostgreSQL |
| Изменить JWT_SECRET | Старые токены перестанут проходить проверку подписи |
| Изменить POSTGRES_PASSWORD в .env при старом volume | Пароль существующей роли сам не обновится |
| Включить debug=True FastAPI в production | Traceback может раскрыть внутренние детали |
| Удалить bind mount | Изменения локального кода не попадут в работающий контейнер |
| Удалить --reload | Файл виден, но процесс не перечитает его автоматически |
| Изменить только модель существующей таблицы | create_all не выполнит ALTER TABLE |

## 12. 28 вероятных вопросов

1. **Почему эта тема?** Три простые сущности и понятная гонка за ограниченные места.
2. **Почему FastAPI?** Валидация Pydantic, удобные зависимости и встроенная документация OpenAPI.
3. **За что отвечает Uvicorn?** Принимает HTTP и запускает ASGI-приложение.
4. **Что такое ORM?** Связывает Python-объекты с таблицами и формирует SQL.
5. **Где пароль?** В users.password_hash, Argon2id; исходный пароль в БД не сохраняется.
6. **JWT шифрует данные?** Нет, подписывает; payload можно прочитать.
7. **Разница 401 и 403?** 401 — нет действительной аутентификации, 403 — не хватает прав.
8. **Что такое IDOR?** Доступ к чужому объекту путём подстановки id без проверки владельца.
9. **Как получить ADMIN?** Через локальную команду manage; публичная регистрация даёт только USER.
10. **Почему недостаточно проверить count?** Между проверкой и INSERT другой запрос может занять место.
11. **Чем помогает FOR UPDATE?** Блокирует строку курса на время транзакции, сериализует запись.
12. **Unique защищает вместимость?** Нет, только пару user_id/course_id; вместимость защищает транзакция.
13. **Что делает commit?** Фиксирует изменения и завершает транзакцию, освобождая блокировки.
14. **VUsers равны RPS?** Нет, частота зависит от задач, пауз и задержки ответа.
15. **Что такое Ramp-Up?** Период постепенного запуска всех виртуальных пользователей.
16. **Зачем p95, если есть среднее?** Показывает медленную часть ответов, которую среднее может скрыть.
17. **Почему 409 не всегда ошибка теста?** Отказ при полной группе — правильный бизнес-результат;
    его считаем отдельно от сбоев сервера.
18. **Можно ли утверждать предел по одному тесту?** Нет, нужны повторы и разные уровни нагрузки.
19. **Чем image отличается от container?** Image — шаблон, container — работающий экземпляр.
20. **Зачем Compose?** Согласованно запускает API, БД, сеть, volume и настройки одной командой.
21. **Почему БД называется db в URL?** Это DNS-имя Compose-сервиса внутри сети.
22. **Что сохраняет данные?** Named volume, независимый от жизненного цикла контейнера.
23. **Что делает down -v?** Удаляет также volume, поэтому уничтожает данные этой среды.
24. **Зачем healthcheck?** Проверяет реальную готовность, а не просто существование процесса.
25. **Что даёт multi-stage?** В финальном образе остаются нужные runtime-файлы, без материалов сборки.
26. **Зачем bind mount и reload вместе?** Первый доставляет изменения файла, второй перечитывает код.
27. **Что делает CI?** На PR/push main автоматически запускает линтер, тесты и проверки Docker.
28. **Что здесь реально проверено?** Свериться с docs/VERIFICATION.md и результатами своего запуска.
    Не утверждать, что SQLite доказывает корректность блокировок PostgreSQL.

## 13. Практический план на 120 минут

Установку Docker/Python и загрузку образов сделай заранее: они зависят от интернета и не входят в 120 минут.

| Минуты | Действие | Проверка понимания |
|---|---|---|
| 0–15 | Запустить Compose, пройти /health и Swagger | Сам объясняешь client → API → DB |
| 15–30 | Регистрация, роли, 401/403 и запись на один курс | Умеешь показать USER против ADMIN и IDOR |
| 30–45 | Открыть enroll, models, security | Объясняешь гонку двумя запросами и роль блокировки |
| 45–65 | Выполнить normal и spike, открыть CSV/графики | Отличаешь реальные 409 от технических ошибок |
| 65–80 | Разобрать RPS/p95/CPU/RAM своего запуска | Называешь условия и ограничения измерений |
| 80–95 | Прочитать Dockerfile и Compose, выполнить verify_docker | Объясняешь образы, контейнеры, healthcheck, volume |
| 95–105 | Показать bind mount/reload и две среды | Понимаешь разницу dev и production |
| 105–115 | Ответить вслух на 28 вопросов | Исправляешь непонятные места по исходникам |
| 115–120 | Репетиция рассказа и последовательности команд | Без подсказки находишь файлы и результаты |

Если времени мало, важнее честно объяснить свой запуск, блокировку и сохранность данных,
чем запомнить определения всех библиотек. При неожиданных результатах показывай журнал
и говори, что именно не прошло, а не подгоняй числа под ожидаемые.
